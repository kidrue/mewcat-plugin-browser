# 开发约定

## 规范维护

本文件的增删和修改（含本条）须由用户单独明确提出。开发、重构、数据升级和代码清理须遵守本文件，任务授权不包含修改本文件。

## 通用 React 开发约定

新增功能须先分析可行性、技术选型和实施方案，经用户确认后再实现。

### 目录与依赖

- `src/` 下的源码目录最多两层。采用 `features/` 时，`src/features/<feature>/` 已是第二层，`src/features/<feature>/test/` 属于禁止的第三层。子函数、实例、辅助代码和测试按职责拆成同级文件，独立业务模块在 `features/` 下并列。目录深度例外由项目逐项列出路径和原因。
- 跨模块复用的 Hook、Context、状态和外部服务封装分别放入 `hooks/`、`contexts/`、`state/`、`services/`。共享类型、常量、工具和样式分别放入 `types/`、`constants/`、`utils/`、`styles/`。
- 入口负责初始化和挂载，页面组合业务模块与 UI，业务模块持有业务规则，并通过服务层访问外部系统。业务模块不反向依赖页面或入口。
- 通用组件和公共工具不得依赖具体业务模块。通用组件通过 Props 和回调交互，专用 UI 放在所属业务模块内。
- 跨模块通过模块公开入口导入，模块内直接引用具体文件。避免循环依赖。

### 组件、Context 与 Hook

- `src/components/` 根目录只允许 `index.ts` 作为独立文件。每个独立组件模块使用与主组件同名的目录，主组件、原子组件和辅助文件同级平铺。目录内的 `index.ts` 导出公开成员。需要公开整个工具模块时可用 `export * from "./utils"`。
- 每个实现文件只定义一个 React 组件。仅用于局部展示或轻量适配、且只供同文件使用的小型私有组件可放在该文件的顶层，如局部 `Tag` 或只封装拖拽绑定的 DnD `Item`。需要跨文件复用或承担独立业务逻辑时，拆为同级文件。
- 主组件负责组装和协调，原子组件保持单一职责。按需用 `types.ts` 声明类型、`constants.ts` 存放固定配置、`utils.ts` 存放工具函数、`styles.ts` 存放组件样式。
- 独立文件中的组件使用具名 `export const Test: React.FC<TestProps>`。同文件的小型私有组件使用 `const Test: React.FC<TestProps>`。有输入就声明 `<组件名>Props`，在同级 `types.ts` 中定义并通过 `import type` 引入。仅接收 `children` 也须声明 Props。无输入时使用 `React.FC`。
- 使用 `React.memo` 优化或 `React.forwardRef` 透传 `ref` 时，可具名导出包装结果。有 Props 时仍须显式声明对应类型。
- Context 封装为独立 Provider 组件，负责管理状态、组织上下文值并渲染 `children`，按需提供读取 Hook。
- Hook 按类型分组，组间空一行。建议依次为 `useContext`、`useState`、`useRef`、`useMemo`、`useCallback`、`useEffect`，有先后依赖时按实际依赖排列。
- 在组件渲染体内声明的具名函数用 `useCallback` 包裹。传给 Hook、`map`、`filter` 的就地回调可直接传入。`useMemo`、`useCallback` 和 `useEffect` 的依赖数组按实际引用填写。
- 每条代码注释写成一句、一行，说明业务意图或边界约束。

### 命名、导入与规则归属

- 组件、类和类型使用 `PascalCase`，函数和变量使用 `camelCase`，自定义 Hook 使用 `use` 前缀，业务目录名使用 `kebab-case`。
- 导入顺序遵循项目配置，保留副作用导入所需的执行顺序。
- 默认值、状态含义和业务规则只在所属模块定义一次，供其他模块复用。可由 Props 或 state 推导的值直接派生，避免保存和同步重复状态。

### 输入、失败与数据升级

- API 响应、跨环境消息和持久化数据在进入业务前校验。业务函数明确输入和返回类型，使调用方能区分成功、空结果和失败。异步 UI 还要区分加载中和空结果。
- 业务代码只处理当前数据结构和业务规则。历史数据用独立脚本、数据库迁移或存储升级处理，版本判断和旧字段读取留在迁移边界。业务入口只接收符合当前结构且通过校验的数据，明确处理升级失败。
- 数据结构变更时，验证已有数据的升级结果、重复执行及失败重试。项目有已发布接口的兼容要求时，在接口边界处理。

### 实现替换与验证

- 替换实现后，清理失效入口、无用导出、注释掉的旧实现和仅覆盖旧实现的测试，保留现行业务行为的测试覆盖。
- 将源码目录深度、组件目录和公开入口、格式、Lint、类型检查、相关测试与构建纳入 CI。失败时应能定位到违规路径或失败用例。

## 浏览器扩展补充约定

- 遵循[仓库约定](../../AGENTS.md)。新增功能分析须考虑 Chrome MV3、CSP 和跨域限制。已发布共享协议的兼容要求以仓库约定为准。
- WXT 注册、初始化和挂载位于 `src/entrypoints/`，页面布局和页面级状态位于 `src/pages/`，网页集成位于 `src/contents/`，翻译及相关业务按功能放入 `src/features/`。
- 目录深度例外为 `src/public/`，静态资源可按类别分目录。运行时资源位于 `src/public/assets/`，通过 `assets/...` 访问。`@wxt-dev/auto-icons` 从 `assets/icon.png` 生成的图标通过 `icons/...` 访问。
- 使用 `React.forwardRef` 保持现有组件在 React 18 下的 `ref` 接口。
- 注入网页的类名和 DOM 标识使用 `mewcat-` 前缀，属性使用 `data-mewcat-` 前缀。修改已有标记时同步检查抽取、渲染、清理和跨环境通信。
- 专题文档遵循仓库的文档存放约定。源码入口、翻译链路、模型配置和缓存见[扩展架构](docs/architecture.md)，发布与 Sentry 配置见[发布手册](docs/chrome-web-store-automation.md)，人工验收见[测试说明](test/README.md)。
